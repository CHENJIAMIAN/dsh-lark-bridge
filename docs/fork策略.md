## 二、一个被我自己搞错过的判断

**错的说**：lib/ 构建产物混进每个提交，所以 PR 不可行。

**事实**：上游自己也这么提交。举 `3821f75`（上游修 session 死锁）：

```
lib/{types-Bu9SB6E3.js => types-BcolOw5x.js} | 271
src/session.ts                              | 238
tests/session.spec.ts                       | 205
```

源码、测试、产物一起提——**这是仓库惯例，不是分叉理由**。以后别再拿它当借口。

## 三、真正该看的判断标准

一个改动值不值得提 PR，只看一件事：

> **上游合并它，会不会改变别人的默认行为？**

- **不会** → 该提。这是纯增益，上游没理由拒绝。
- **会** → 别提，自己留着。这不是"上游不识货"，是你把个人工作流当成了通用需求。

## 四、日常怎么运作

```sh
# 上游当 bug 来源，不当汇报对象
git fetch upstream
git log --oneline HEAD..upstream/main        # 上游有什么新的
git cherry-pick <修 bug 的提交>               # 挑着拿回来

# 自己的主线
git checkout main                            # 所有功能都落在 main
git checkout -b feat/xxx                     # 一次一个功能
git checkout main && git merge feat/xxx
```

**三条纪律**：

1. **一个分支一个功能**，做完合回 main 就删。别再让 `feat/xxx` 上堆 32 个提交。
2. **改完就 `pnpm build` 再提交**——插件运行加载的是 `lib/`，产物和源码必须同步进仓（上游惯例）。
3. **README 中英必须同步**，`node scripts/check-readme-parity.mjs` 会拦；测试计数也会被 `tests/docs-consistency.spec.ts` 拦。

## 五、别再为这件事内耗

「fork 当主线、上游当 bug 来源、好的顺手提、改默认的留」——这四句就是完整答案。
不追求和上游一致，也不追求 PR 全通过。**跟着上游走，不等于要把每个改动都交上去。**
