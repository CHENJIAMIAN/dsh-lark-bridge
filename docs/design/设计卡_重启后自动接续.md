# 设计卡：重启后的自动接续（dsh-lark-bridge）

> 状态：现行设计 · 2026-11-09 建档 · 运营方提问触发

## 1. 两个问题，同一类失效

> 重启后目标丢失了吗 怎么没有见你继续
> 还有一个问题是，重启后定时任务会不生效了，这个也要看能不能解决

两件事表面无关，根子一样：**宿主的持久状态跨过了重启，驱动它的东西没有**。

- **目标**：`phase=active` 存在会话日志里，跨重启；但续跑授权（activation）是
  进程内的，重启后一律 `disarmed`，要等下一条人类消息才重新上膛。后台任务永远
  等不到那条消息。
- **定时任务**：`schedule.json` 里任务完好；但调度器不按时钟触发——投递记录显示
  09:00 的任务 15:06 才发，所有积压的都在同一分钟补上，说明它是在某个后续事件上
  追赶，而不是到点就发。

## 2. 目标续跑

`src/goal-watch.ts` 记录「哪些会话有 active 目标」到
`~/.dsh/lark-bridge-goals.json`：

- 按会话覆盖刷新（一个跑几十轮的目标只占一行）
- 7 天不刷新自动过期
- 原子写（写临时文件再 rename），坏文件读成空而不是让启动失败

**只记 `active`**。暂停、阻塞、完成、清除一律摘除——用户手动暂停的目标不能因为
部署一次就自己活过来。

开机 `resumeGoalsBootDelaySeconds` 秒（默认 8，宿主还在组自己的服务）后：

1. `ladder.resume(sessionId)` 重新打开会话
2. **重建 chat 绑定**——目标续跑会产生输出，没有 renderer 就无处可去
3. `goals.get(agent)` 确认仍是 `active && disarmed`，才 `resume`
4. 已是 armed 或已结束的从名单摘除

重建绑定是这一步的关键，也是它比 `autoResumeGoals` 强的地方：后者只在收到人类消息
时上膛，一个没人在的部署里等于没有。

## 3. 定时任务漏发

`src/schedule-watchdog.ts` 是纯函数：给定任务表和当前时间，列出「逾期但没有对应
投递记录」的实例。

判定故意窄：

- `status === 'active'`（暂停不算）
- `scheduledAt` 在过去
- **`lastDelivery.scheduledAt` 与该次不相等**——比对的是「这一次有没有投递」，
  不是「有没有投递过」；后者会让一个日报在跑成功一次后永远不再报警
- 逾期在窗口内（默认 24 小时）

桥每 60 秒读一次 `~/.dsh/storages/schedule.json`，启动 20 秒后先查一次（重启正是
积压出现的时候）。同一个「任务+时间点」只提醒一次。

**提醒而不是自动执行**：派发等于起一轮 agent，那是宿主的权限；而且 09:00 的清理
任务在 15:06 被人手动点一下，和它自己突然开始跑，是两件事。所以卡片给一个
「现在执行」按钮。

按钮也不伪造投递：它把调度器本该发的那条消息**按入站路径重放**，授权、设备退位、
云端仲裁照常生效；发起人是按按钮的那个人，所以可归属。跳过这条路径去直接起 agent
才是真正的坑——退役设备上一次任务跑两遍就是这么来的。

## 4. 配置

| 项 | 默认 | 作用 |
|---|---|---|
| `autoResumeGoals` | false | 原有：收到人类消息时上膛 |
| `resumeGoalsOnBoot` | true | 新增：开机主动上膛，需配合上一项 |
| `resumeGoalsBootDelaySeconds` | 8 | 新增：开机后等多久再动 |
| `notifyOverdueSchedules` | true | 新增：漏发提醒 |
| `overdueScheduleWindowHours` | 24 | 新增：多旧的漏发还值得提醒 |

## 5. 失败路径

| 情形 | 处理 |
|---|---|
| 名单文件坏/不存在 | 读成空，不阻止启动 |
| 目标已暂停/完成 | 从名单摘除，不重复尝试 |
| `resume` 抛错 | 记一条运维通知，继续处理下一个 |
| schedule.json 缺失或坏 | 当没有逾期任务，不打扰聊天 |
| 任务没有绑定会话 | 跳过（没有群可发） |
| 按按钮时任务定义已读不到 | 回一句「读不到了，没法补跑」 |

## 7. 追加：自动补发（可选，默认关）

前面第 3 节写的是「提醒而不是自动执行」。目标要求的是「补发」，所以在提醒之上补了
自动那条路，用 `autoDispatchOverdueSchedules` 控制：

- **开**：窗口内的漏发直接重放执行，发起人取 `senderAllowlist` 的第一个授权用户，
  跑完回一条文字说明
- **关（默认）**：行为不变，发橙卡等人类点「现在执行」

默认关是有意的。人排的任务里有会删东西的，「03:00 它自己跑起来」和「我 15:06 点了
一下」是两件事，不该由桥替部署方决定。

两种模式共用 `dispatchOverdue`，走的是同一条入站路径，所以授权、设备退位、云端仲裁
一个都不跳过。

### 真机验证暴露的第二个缺陷

自动补发跑起来之后，回执发不出去：

```
outbound send failed: … not a valid {open_message_id} … Invalid ids: [overdue-1794237122289]
```

补跑把 prompt 重放成入站消息，`messageId` 是合成的 `overdue-<ts>`，而桥照常拿它去
`aim` 回复目标、加 reaction。飞书只认 `om_` 开头的真实消息 id。

修法不是改那个 id 的形状，而是让入站处理区分两种消息：**只有 `om_` 开头的才 aim、
才 ack**。合成消息因此回成普通消息，不进回复引用、不挂表情。
