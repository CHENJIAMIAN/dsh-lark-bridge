# 设计卡：工作流进度改成一张卡（dsh-lark-bridge）

> 状态：现行设计 · 2026-11-09 建档 · 运营方截图反馈触发

## 1. 背景：运营方发来一张群聊截图

> 你先别调用工具，我会发给你一张图片，你看一下，为什么会这么乱？能不能理一下
> 当前多子代理或者 workflow 的回复，应该是有问题的 或者说用户体验是很差的

截图里 11 条消息，实际只有 5 类事件：

```
🧩 工作流「scan-pitfalls-batch」开始，派出子任务…
🗂️ 阶段：精读
🔀 派出子代理 · scan-pitfalls-batch child 1（进展会实时更新，完成后一并汇报）
· chunk-65.txt 启动…
🔀 派出子代理 · scan-pitfalls-batch child 4
🔀 派出子代理 · scan-pitfalls-batch child 3
🔀 派出子代理 · scan-pitfalls-batch child 2
· chunk-66.txt 启动…
· chunk-67.txt 启动…
· chunk-68.txt 启动…
✅【子代理完成】scan-pitfalls-batch
```

四个子代理，产生了九条消息。

## 2. 根因：同一件事被两个通道各报一遍

| 通道 | 事件 | 文案 |
|---|---|---|
| subagent catalog | 每次委派 | `🔀 派出子代理 · <label>` |
| workflow agent-start | 每个成员 | `  · <label> 启动…` |

`child 1..4` 和 `chunk-65..68` 是**同一批四个子代理**：前者是 subagent 通道给的 label，
后者是 workflow 成员 label。两条通道互不知情，于是每次委派在聊天里出现两次。

再叠加两件事：

- **逐条**：每个事件一条独立消息，68 个成员就是 136+ 条。飞书手机端一屏装不下，还要
  触发每聊天频率限制——`00394bd` 提到的「重放队列整夜滞留」就是被这个限制打回来的。
- **乱序**：`child 1 / 4 / 3 / 2`。并发派遣，消息到达顺序随机，读者拼不出因果。

`00394bd` 已经加过 `workflow-narrator`（2 秒窗口折叠成计数行），但它只解决了
「member 事件逐条」，没解决「两条通道重复」，也没给出整体视图——读者仍然要自己
把一堆消息拼成「现在到哪了、哪个失败了」。

## 3. 设计：一条 run 一张卡，原地重写

`src/workflow-card.ts` 取代 `workflow-narrator.ts`（后者连同测试一起删除）。

卡片内容：

```
🧩 工作流「scan-pitfalls-batch」            ← header，蓝；结束转绿/灰/红
阶段 精读                                   ← phase 事件
启动 68 · ✅ 12 · ❌ 1 · ⏹️ 0
失败 chunk-33.txt 等 2 个                    ← 有失败才出现
进行中 · 已用 2m13s                          ← 结束换成「用时 2m13s」
```

**一条 run 一条消息**：`run-start` 立刻发卡（开局沉默 1.2 秒会被读成卡死），之后所有
成员事件、阶段变化都走 `updateCard` 重写同一张。同一 chat 的第二次 run 复用同一个
`messageId`，不会积累卡片。

**更新合并 1.2 秒**：8 个成员在同一秒内结算时，卡片每秒被重写 8 次既超过飞书频率限制，
人也看不清。合并窗口内的多次变更只写一次。

**只列失败者，不列全体**：读者不扫 68 个名字，只问「完没完」「谁挂了」。所以成功的
只计数，失败的列名字，超过 5 个折成「等 N 个」。

**`workflow/log` 仍然单独发声**：narration 是工作流脚本主动要说的话，不是进度快照，
塞进一张会被反复重写的卡里反而看不见。

## 4. 顺手修掉的重复：workflow 运行期间不播「派出子代理」

`bridge.ts` 里 `announceSubagents` 加了一个前置条件 `!workflows.isActive(chatId)`：
workflow 跑着的时候，新派的子代理就是它的成员，卡上已经报了；再播一条独立的
「派出子代理」正是「一次委派读成两件事」的来源。

**已知取舍**：workflow 运行期间，用户手动让我派的**独立**子代理也不会单独播报。
它仍然会出现在 subagent 面板卡里，只是没有那一行开场白。判定用「这个 chat 有没有
活跃 run」，不追溯父子关系——宿主的 `tool-workflow/agent-start` 不带 childId，
无法精确关联，而这个近似在真实用法里几乎不会错。

## 5. 失败路径

| 情形 | 处理 |
|---|---|
| 卡片发送失败 | `onFailure` 通知运维；run 继续计数，下个窗口重试 |
| `updateCard` 失败 | 同上；首卡仍在，读者至少看得到 run 开始了 |
| 端口没有 `updateCard`（测试替身） | 退化成只有开场卡，不崩 |
| 事件先于 `run-start` 到达 | 忽略（没有 state 就没有可画的进度），不新建半张卡 |
| 重复投递 `run-start` | 忽略，不重置已经在跑的计数 |
| 进程退出时有待写窗口 | `dispose()` 清掉所有定时器 |

## 6. 测试

- `tests/workflow-card.spec.ts`（8 条）：一次 run 只发一条消息、成员事件只重写不新增、
  计数正确、失败者列名且超额折成计数、阶段上图、结束定格颜色、同 chat 复用 messageId、
  无 `updateCard` 时降级、ghost 事件被忽略。
- `tests/plugin.spec.ts`（改写 1 条）：`tool-workflow/*` 四个事件的真实桥接——开局卡、
  阶段与计数落进 `updateCard`、**期间不新增聊天消息**、`workflow/log` 仍发 markdown。
- `tests/workflow.spec.ts`（精简到 1 条）：模块只剩事件类型和 narration 行。
